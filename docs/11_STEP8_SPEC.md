## 0. 这一步在解决什么

用户的原话：**「我希望这个也能像 CLAUDE.md 文档一样读取自己的全局 / 局部规则的 md 文档」**。

这句话不是一个锦上添花的功能请求，它是 `06` 第 4 节那条要求的前半截。
那一节要求「Council 成员的指令环境由 Council 自己构造，而不是继承用户的全局规则文件」，
它有两半：

- **后半截「不继承用户的」已做**（`6530839`）：claude 加 `--safe-mode` 之后，
  用户 `~/.claude/CLAUDE.md` 的痕迹在实测里消失了。
- **前半截「Council 有自己的那份」就是本步第 1 节**：切断继承之后，
  成员的指令环境现在是空的，只剩 Council 注入的那一小块身份文本。
  没有规则文件，这个空缺就只能靠把规则手抄进 `config.toml` 的 `role` 字段填。

所以这两件事必须一起看：**切断继承让规则文件从「便利」变成「必需」**。

本步还顺带到期两笔债，它们都是被第 1 节逼出来的，不是顺手做的：

1. **未决 #15**（`MaxPromptBytes` 量 prompt、OS 限整条命令行）。规则文本在 grok 与 agy
   两家上直接落进 argv，几 KB 的规则会把那段漏风从「理论上」变成「必踩」。
2. **WORKSPACE 档**。`06` 第 2 节现在有了实测的写入边界一行，
   「哪家能开 WORKSPACE」第一次有了可以援引的证据，不必再一刀切全拒。

## 1. 规则文件体系

### 1.1 两级，位置固定，绝不按 cwd 发现

| 级别 | 位置 | 怎么来的 |
|---|---|---|
| 全局 | `~/.council/COUNCIL.md` | 固定路径，自动发现，不由配置文件指定 |
| 局部 | 配置文件里的 `rules_file` 键 | 显式写出来；相对路径相对**配置文件所在目录**解析 |

两条都不按当前工作目录发现。理由是 `06` 第 4 节已经裁过的那条：
按 cwd 发现会让入场费与行为随启动目录漂移、不可复现。
`runner.go` 里那段拒绝空 `workDir` 的注释说的是同一件事。

**全局那份为什么不许配置文件覆盖。** 它固定在 `~/.council/COUNCIL.md`，
与 `config.toml` 的**默认**位置同目录，但不跟着 `--config` 走。
一份从别处拿来的项目配置不应该能重新定义「什么算全局」——
那正是「全局」这个词的全部含义。测试与异机用环境变量 `COUNCIL_GLOBAL_RULES` 换路径，
解析顺序与 `ResolveConfigPath` 同构：环境变量 -> `~/.council/COUNCIL.md`。

**局部那份为什么挂在配置文件上而不是 team 上。** 查过了：`Teams` 今天只被
`/teams` 列出来看（`repl/commands.go:383`），**没有接进会话**——
会话的成员是一个个 join 进去的，与 team 无关。把局部规则挂在 team 上会当场交付一个死键。
等 Step 9 把 team 接进会话，再加第三级；第 1.3 节的渲染顺序已经给它留了位置。

**文件不存在 = 没有规则，正常路径，不报错。** 这与 `config.toml` 不同（那个找不到是致命的）：
规则文件是可选的。但**存在却读不出来**（权限、是目录、编码坏）是硬错误，
与配置加载失败同一套处置：写 `Err`、不进 REPL。
「读不出来就当空的」会让一次 I/O 故障静默地把成员的指令环境掏空。

### 1.2 三家不对等，规格里不许假装一样

这张表从 `06` 4.1 原样带过来，因为它决定了同一份 `COUNCIL.md` 在三家身上**不是同一个东西**：

| | Council 规则的地位 | 载体 | 用户 `~/.claude/CLAUDE.md` |
|---|---|---|---|
| claude | **唯一**指令源 | `--append-system-prompt-file`（文件，不占 argv） | 已被 `--safe-mode` 切断 |
| grok | **增量**，叠加在用户全局规则之上 | `--system-prompt-override`（**占 argv**） | 切不断，三招都试过 |
| agy | 大概率是唯一来源，但另有自家体系未测 | 首轮正文前缀（**占 argv**） | 没有证据表明它读 |

**两条必须写进规格、不许猜的**：

- **grok 上冲突时谁赢，未测。** 用户的全局规则说 A、Council 的规则说非 A 时，
  grok 听谁的，没有实验数据。不要在文档、代码注释或 `/rules` 输出里写任何倾向性措辞。
  按 `[未验证]` 记。
- **agy 那一格是「没拿到正向证据」，不是「已证明隔离」**，见 1.2.2。

所以 agy 这一格的准确措辞是：「不继承用户的 `~/.claude`（两项负向证据）；
自家 project / skill 体系是否带进指令，未测」。`/rules` 就按这个措辞显示。

  与 claude / grok 的「进了缓存前缀之后几乎白送」完全不同。

### 1.3 渲染顺序：共享的在前，专有的在后

`renderIdentity` 的产出改成三段，按此顺序：

```
1. 全局规则正文     （非空时）
2. 局部规则正文     （非空时）
3. agent 自己的身份  （今天已有的那段：You are X (id=y). / Provider: z / role）
```

**为什么是这个顺序。** 未决 #1 已测：**缓存按内容命中，不按会话**
（同 provider 的两条互不相干的会话，前缀逐字节相同时第二条 `cache_read` 直接命中）。
共享内容排在前面，同一家 provider 的多个 agent 就共享更长的公共前缀；
排在后面则一个字节都共享不到。这个顺序本身零成本，不排是白扔。
（只在 grok 上测过，claude 与 agy `[未验证]`；但排序即使无效也不会更糟。）

**硬性要求：两段规则都为空时，`renderIdentity` 的输出必须与今天逐字节相同。**
这不是洁癖——它加上 1.5 节的迁移，共同保证「不用规则文件的人升级之后一条会话都不重建」。
用例要直接钉住这一条：空规则渲染结果与 golden 文件相等。

段间用一个空行分隔。每段规则正文前加一行 ASCII 标签
（`# Council rules (global)` / `# Council rules (project)`）。
**加标签的理由不是好看**：grok 那边切不断继承，出问题时你唯一的窗口是让成员自述
它看到了什么；没有标签，它没法告诉你那条指令来自哪个文件。二十来个字节买这个，值。

### 1.4 规则文本进指纹，但存的是摘要不是全文

规则文本进了身份块，身份块整段进缓存前缀，所以**它必须进 `IdentityFingerprint`**，
否则改规则会拿着按旧规则建好的前缀继续 `--resume`：模型按旧规则说话、
库里记着新规则，没有任何一层报错。这正是 `session.go` 那段注释在防的情况。

**两个新字段，不折进 role。** 折进 role 的话，用户改了 `COUNCIL.md`，
`ErrIdentityDrift` 会报「role 变了」——指着一个他没动过的字段。

**两个新字段存摘要，不存全文。** `packFingerprint` 今天存的是全文
（`session.go:73` 明写：不用哈希，是为了在 drift 报错里点名旧值），
而 `identity_fp` 这一列每条 provider 会话存一份。role 继续存全文，
规则动辄几 KB，存全文只会把库撑大而换不到任何表达力——
一段 5 KB 的旧规则原文在终端上没法给人看，能给人看的是「变了多少、变成了什么」。

格式：`<字节数>/<sha256 前 12 位十六进制>`，例如 `4821/3f2a1b9c4d5e`。
于是 drift 能报「全局规则：4821 字节 3f2a1b9c4d5e -> 4903 字节 9c1b7e0a2f44」。

**规则为空时该段是空串，不是空串的哈希。** 这条很重要，1.5 的迁移正好靠它对上。

### 1.5 schema v3：把四段指纹迁成六段

`fpFieldCount` 从 4 变 6 有一个直接后果：**库里现存的每一条 `identity_fp` 都是四段的**，
`fingerprintFields` 会在长度校验处 `ok = false`，于是全部按「指纹整体不符」处理。
从库读回那一支的处置是**静默作废重建**（`runner.go:183`），
所以升级之后第一次 `/ask`，每条活着的 provider 会话都会悄悄重建一次，
每条一次入场费（D-4：0.4 到 1.0 美元）。**没有任何一层会说话。**

**处置：schema v3，把每一行的 `identity_fp` 追加两个空段（`0:;0:;`）。**

- 规则为空时，迁移后的值与新代码算出来的值**逐字节相等**（靠 1.4 末那条），
  旧会话照常暖着，升级不花钱。
- 规则非空时指纹正确地不符，会话重建——那是对的，前缀真的变了。

**「升级不花钱」这句要加一个限定才算可核对**，因为指纹还漏掉了另一样东西：

> 对 **`6530839` 之后建立的** provider 会话，升级不花钱。

`6530839` 把 claude 的 READ 档从一个 flag 改成四个、给 grok 加了三条 `--deny`，
**发出去的 argv 真的变了，而身份指纹一个字都没动**——`fpFieldTier` 记的是档名
`read`，改前改后都是 `read`。所以那次提交之前建的会话，前缀已经变了而指纹说没变。
这是本片**修不了**的另一个洞，单独记进未决 #18。

**这台机器上有几个受害者：查过了，6 条，全在隔离根下的冒烟测试库里。**
`6530839` 提交于 2026-09-21T01:06:27Z，库里 6 条 provider 会话最晚的一条是
01:05:55Z，差一分钟，全部早于它。但**生产库根本不存在**
（`E:\council-data` 没有这个目录，`~/.council/config.toml` 也没有），
那 6 条是 step5 / step6-smoke / step7-smoke 的一次性产物。
所以这个洞在本机**没有真实受害者**，它是一条流程教训（改 flag 没同裁指纹），
不是一笔要用迁移去补的账。

**为什么不用代码层的兼容垫片**（让 `fingerprintFields` 容忍四段、缺的当空串）：
垫片是永久的，而且它把 `fpFieldCount` 这道长度校验从「严格」变成「看情况」，
下一次加字段时没有人还记得为什么它可以不严格。迁移是一次性的，
而且本项目每一版迁移自带形状声明（未决 #10），这条路是现成的。

这一版**不改任何列**，只改数据。`11a` 要写清楚迁移框架在「形状不变、只改数据」
这一档上的确切形状，别让实现方临时发明。

### 1.6 什么时候读：启动读一次，外加显式 reload

跟着配置文件一起读，一次。这正是用户点名的那个类比——Claude Code 也是会话开始读一次。

**这里要裁的到底是什么，写清楚免得下一个会话重新推：**
争的不是「意外花钱 vs 不花钱」，是**意外被拒的时机**。
因为漂移在两条路上的处置根本不同：

| 什么时候变的 | 处置 | 代价 |
|---|---|---|
| 进程内（会话开着时改） | **拒绝**（`runner.go:162`，`ErrIdentityDrift`） | 不花钱，但下一轮卡住 |
| 跨重启（从库读回时不符） | **静默作废重建** | 每条会话一次入场费，用户不知情 |

「每轮读文件」会让改一个字就在下一轮把所有成员拒掉；「启动读一次」把这个时刻
推到用户自己选的时候。两者都不花冤枉钱——**真正花钱的是那条静默重建**，
而它今天就已经存在，与读不读规则文件无关。规则文件只是让它更容易被触发。

所以本节的交付物有三件，第三件是新的：

1. 启动时与配置一起读，进 `renderIdentity`。
2. `/rules reload` 重读磁盘（见 1.7）。
3. **启动漂移审计**（见 1.7.2）——把那条静默重建变成响亮的。

### 1.7 漂移之后必须有路可走

**这是必做项，不是可选项。** 今天 `/session` 只能看（`repl/ask.go:83`），
`DropProviderSession` 只有 Runner 内部在用。也就是说用户在会话开着的时候改了配置，
下一轮被 `ErrIdentityDrift` 拒绝之后**进程内没有任何一条命令能让他继续**，
只能重启 council 或把配置改回去。规则文件会把这个缺口从「偶尔踩到」变成「必踩」：
编辑 `COUNCIL.md` 正是这个功能存在的意义。

#### 1.7.1 两条命令

- **`/session rebuild <agentID>`**：丢弃这个 agent 在当前会话的 provider 会话。
  必须**五样全丢**（会话 id / 游标 / 成本基线 / `lastTurnAt` / 指纹），
  也就是直接 `DropProviderSession` 删整行，不是只清指纹——
  `10_STEP7_SPEC.md` 第 4 节那条「重建意味着 provider 那边计数器从零开始，
  只作废会话 id 而留着旧基线会让下一轮差值为负、那笔钱静默从账上消失」原样适用。
  执行前在屏幕上说明这会产生一次入场费。
- **`/rules reload`**：重读两个规则文件，报告新旧字节数与摘要、以及**哪些成员会因此漂移**。
  默认**只报告不执行**。真要应用，`/rules reload --rebuild` 才对漂移的成员执行上面那条丢弃。
  分两步是因为一条命令可能一次烧掉几个入场费，那种事必须是用户按下去的。

#### 1.7.2 启动漂移审计

启动时（打横幅之后、进 REPL 之前）把 `provider_sessions` 全表读出来，
逐行用当前的配置 + 规则算一遍指纹，数出有多少行对不上。

- 对不上 0 行：不打任何东西，不制造噪声。
- 对不上 N 行：打一行，写明 N、涉及哪些会话与成员、以及「下次对它们 `/ask` 会各重建一次」。
  （X-39f 订正，2026-09-24：「对不上」有六种原因，其中四种——配置里已无此 agent、provider 不可用、权限档不放行、算不出指纹——
  下次 `/ask` 会在起进程之前被拒、不花钱，不是重建。提示按后果分两句说，见 `11a` §3.5、§6 的订正；已删 agent 留下的悬空行可用 `/session rebuild` 清掉。）

理由：这件事**今天就在静默发生**，只是还没有人被它咬过，因为除了改 model / effort
之外没什么会触发。规则文件把触发条件变成「编辑一个 md 文件」。
一次读全表加字符串比较，代价可以忽略，换掉的是一笔没人看得见的开销。

### 1.8 `/rules` 报什么

一行 header 加逐 provider 一行。逐 provider 而不是一行总计，
因为 1.2 已经说明同一份规则在三家身上不是同一个东西。

每行至少要有：

- 两个规则文件的**解析后绝对路径**与**在不在**（不在就是空规则，正常）
- 各自**字节数**，以及合计
- 这家的**指令隔离位**：`唯一来源` / `叠加在用户全局规则之上` / `未验证`
- **估算代价**，按 1.2.1 分家算：claude / grok 标「进缓存前缀，首轮付」，
  agy 标「无缓存，按轮数乘着付」
- **argv 余量**（只对 grok 与 agy，见第 2 节）：这次组出来的命令行还剩多少字节

外加启动漂移审计那一行的当前值（1.7.2 的同一个函数，两个调用点）。

**token 估算怎么给：不给。** 不要编一个 byte-per-token 常数假装标定过。

这条原本写的是「拿用户那份 `~/.claude/CLAUDE.md` 的约 3754 token 当量级参照」。
**查了，那个数不能用**：那份文件是 15016 字节，`15016 / 4 = 3754` 正好整除 ——
`grok inspect` 报的 token 数是 **bytes/4 这个启发式**，不是真分词。
一个看起来像实测的数字，实际是个除法。这正是本项目一路在防的那类东西，
差点被我自己写进规格当标定值。

所以 `/rules` 只报**字节数**。真要给量级参照，唯一有实测支撑的是这个：
claude 侧加上 `--safe-mode --restricted` 之后 `input_tokens` 从 58023 掉到 29413。
那个差值里同时含 CLAUDE.md、51 个 skill、plugins、hooks、MCP，
以及 `--restricted` 带来的工具定义变化，**不能整个记在规则文件头上**，
但它说明「一份继承来的指令环境」是几万 token 的量级，不是几千。

## 2. 规模即成本，而且在两家上是硬上限

第 1 节把一份用户随手编辑的 md 文件接进了每一轮的命令行。两个后果分开记。

**成本后果**：规则文本在缓存前缀里，每条会话首轮按 `cache_create` 计价，
之后靠 `cache_read` 几乎白送（claude / grok）；agy 没有缓存，按轮数乘着付（1.2.1）。

**硬上限后果**：规则文本在 grok（`--system-prompt-override`，`grok.go:81`）
与 agy（首轮正文前缀，`agy.go:53`）两家上**直接落进 argv**。
claude 那边是 `--append-system-prompt-file` 写文件（`claude.go:91`），不占 argv。

### 2.1 未决 #15 到期：argv 总长闸

今天这道闸是 `checkArgvPrompt`（`provider.go:155`），它**只量 prompt**：

```go
if caps.MaxPromptBytes > 0 && len(prompt) > caps.MaxPromptBytes {
```

未决 #15 记着它的漏风：prompt 刚好卡在 32767 以下，加上 flag 段仍可能越界，
失败来自 `CreateProcess`、报错形状不受我们控制、而且**长度相关**
（同一个 agent 对短需求成功、对长需求失败）。当时没收紧，是因为唯一诚实的做法
要么量出 flag 段的真实字节数、要么编一个余量常数，后者会把「未实测」伪装成「已标定」。

**规则文件让这条到期了**，而且它同时给出了那个诚实做法：
`BuildTurn` 组完 `args` 之后，**量它自己刚组出来的那一条真实命令行**，
不是估、不是留余量。

```
总长 = len(exe) + Σ(1 + len(arg))      // 每个参数前一个分隔空格
```

超过 32767 就在**起进程之前**拒绝，哨兵 `ErrCommandLineTooLong`，
错误文本里点名总长、上限、以及**最大的那个参数是哪个 flag**——
这样用户看到的是「`--system-prompt-override` 占了 28 KB，砍规则文件」，
而不是一个 `CreateProcess` 的数字。

`MaxPromptBytes` 那条旧闸保留，两条不是一回事：一条说「这家的正文通路有上限」，
一条说「这一条具体的命令行太长了」。`11a` 要写明 `09a` 里
「Transport 是 Argv 且 prompt 超 MaxPromptBytes -> ErrPromptTooLong」这句措辞怎么改，
它在冻结契约里（未决 #15 早就预告了要动它）。

引号转义不进这个算式。Go 的 `os/exec` 在 Windows 上按自己的规则加引号，
含空格的参数会变长。32767 是 `CreateProcess` 的上限，我们量的是加引号前的长度，
**所以这个闸偏松**——它能挡住「规则文件太大」这类整数量级的越界，
挡不住刚好卡在边上的那几十字节。这条要写进注释，别让下一个人以为它是精确的。

## 3. 权限档按实测放行（第二片）

`06` 第 2 节现在有了「写入边界实测」这一行，`TranslatePermission` 那条
「Step 6 只放行 read」的一刀切可以换成有证据的判定。

### 3.1 能力位要有区分力

`Capabilities` 加 `WriteBoundary Support`：claude = Yes、agy = Yes、grok = No，
每一格的注释里写清楚是**哪个 flag、怎么测的**（`--restricted` / `--add-dir` /
路径模式静默不生效）。三态 `Support` 本来就是为这种事准备的，
这一位是它第一次真正有区分力。

放行规则，fail-closed：

```
WORKSPACE: caps.WriteBoundary == SupportYes 且 caps.Permissions 列了这一档  -> 放行
           否则                                                          -> 拒绝，点名原因
FULL:      一律拒绝（06 第 2 节：不给编排器自动使用）
```

拒绝时的错误文本要区分两种「不行」：**证明不了**（grok，路径模式静默不生效）
与**没这个档**（claude 的 FULL，`--restricted` 结构性地到不了）。

### 3.2 开 WORKSPACE 之前必须先修工作目录

`app.go:117`：

```go
dir := filepath.Join(dataDir, "workdir", id)
```

路径里**只有 agentID，没有会话 id**。今天全是 READ 档，没人写盘，所以没事。
一旦放行 WORKSPACE，两场会话里的同一个成员会写进同一个目录、互相盖文件，
而 `--restricted` 与 `--add-dir` 的边界正好锚在这个目录上，
也就是说边界守住了「别写到外面去」，却守不住「别写到另一场会话的东西上」。

**订正（2026-09-21，实测推翻了「一律隔离」）。** 这里原本写的是
「改成 `<dataDir>/workdir/<convID>/<agentID>`」，一律隔离。**那个代价过高。**

**实测**（原件 `E:\Isolating_test\council\oq-cwd-prefix\RESULTS.md`，
直接调 grok CLI、零成本）：其余参数逐字节相同、只换 `--cwd`，

| 轮次 | cwd | input_tokens | cache_read |
|---|---|---|---|
| run1 | alpha | 18945 | 128 |
| run2 | alpha | **1** | **19072** |
| run3 | **beta** | 18945 | 128 |

run2 是对照组（未决 #1 测过前缀按内容命中），它命中了；
run3 只换 cwd 就回到 run1 的冷启动数字。
**工作目录进模型可见的前缀，换一个 cwd 就是一次完整入场费。**
一律隔离等于让 5 个成员 3 条会话付 15 次入场费而不是 5 次。

**改成按档位分**：

| 档位 | 工作目录 | 理由 |
|---|---|---|
| READ | `<dataDir>/workdir/<agentID>`（**不变**） | 它们不写盘，共用省下那次冷启动。claude 会往那里写 `council-role.txt`，但同一个 agent 的身份块与规则不随会话变，内容逐字节相同 |
| WORKSPACE 及以上 | `<dataDir>/workdir/<convID>/<agentID>` | 按会话隔离，代价是那次冷启动 —— **但只有真会写盘的成员才付**，而写盘的本来就是少数（`06` 第 3 节：五个角色里只有 Executor 要写） |

**附带好处**：READ 的路径不变，所以第二片落地时**既有会话一条都不会漂移**；
一律隔离的话全部要重建一次。

连带一处改动仍然要做：今天这些目录是启动时一次建齐的（那时还没有会话 id），
WORKSPACE 那一支改成**每轮起进程前 MkdirAll**。

**这条是 WORKSPACE 的前置，不是并行项。** 顺序写死：先改目录，再开档。

**这一轮也回头证明了未决 #18 把工作目录收进前缀摘要是对的** ——
那不是「fail-closed 的过度近似」，工作目录真的在前缀里。

### 3.3 开 WORKSPACE 之前还要改一处：`/rules` 的余量探针

`RulesReport` 现在「每家 provider 取 agent id 字典序最小的那个 agent」来组探针命令行。
今天三家各一个 agent，这没问题。**开了 WORKSPACE 之后就有问题**：
同一家 provider 下可能一个 agent 是 READ、另一个是 WORKSPACE，而两档的 flag 段不一样长
（claude 的 WORKSPACE 多一个 `acceptEdits`），余量只按字典序第一个算就是错的。
更难看的是 grok：它**拒绝** WORKSPACE，若字典序第一个恰好是 WORKSPACE 档的 agent，
那一行会印「不适用」，把同一家里其实好好的 READ agent 一起盖掉。

**改法**：余量探针按 `(provider, tier)` 分组，不按 provider。
现在写这一句，比第二片再发现便宜。

## 5. 验收

第一片（规则文件）算完成，必须同时成立：

1. `go build` / `go vet` / `go test ./...` 全过。
2. **空规则的渲染结果与升级前逐字节相同**（golden 用例钉死），
   且 v3 迁移之后一条既有 provider 会话都不重建（用例造一条四段指纹的旧行验证）。
3. 非空规则下：`/rules` 报得出两个文件的路径、字节数、逐 provider 的隔离位；
   改一个字之后 `/rules reload` 报得出摘要变化与将要漂移的成员名单，且**默认不执行**。
4. `/session rebuild <agent>` 之后下一轮走 Fresh 路径，且**五样全丢**
   （用例断言 `DropProviderSession` 被调用，不是只清指纹）。
5. 启动漂移审计：0 行时不打印，N 行时打印且数字正确。
6. argv 总长闸：造一个超长规则文件，grok 与 agy 都必须在**起进程之前**拒绝，
   claude 不受影响（它走文件与 stdin）。

   **但哨兵不是同一个，这条本来写错了，订正如下**（测试方照契约写用例时发现的）：

   - **grok**：规则进 `--system-prompt-override`，不经正文通路，
     所以撞的是新闸 `ErrCommandLineTooLong`。
   - **agy**：规则被折进 argv 的 prompt（`agy.go` 首轮拼在正文最前面），
     于是先撞 `BuildTurn` 里**已有的那道** `MaxPromptBytes` 闸，
     报 `ErrPromptTooLong`，**根本走不到** `spawnProcess` 的新闸。
     只有当 Role 大小恰好卡在 32767 以下的那条窄缝里、而整条命令行越界时，
     新闸才对 agy 生效——那条窄缝正是未决 #15 承认自己关不上的那一段。

   **两条都是「起进程之前 fail-closed 地拒绝」，行为是对的**，只是哨兵不同。
   验收断言要按 provider 分开写，不要写一个统一的 `errors.Is(err, ErrCommandLineTooLong)`。

   **「错误文本点名 flag 名」这条也要按家看**：判定规则原本只认 `--` 开头的前一个参数，
   而 grok 与 agy 的正文都绑在**单横杠 `-p`** 上。所以最长参数是正文时，
   这两家会报成 `args[N]` 而不是 `-p 的值`。**修法是把前缀判定从 `--` 放宽到 `-`**，
   这对两家同时有效；放宽的风险（把一个以减号开头的**值**误当成 flag）在本项目的
   三个适配器里不存在，但要在注释里写明这是个启发式，不是解析。
7. **真机**：三家各跑一轮，规则文件里放一条可验证的指令
   （例如「回答的末尾加一行 RULES-OK」），看三家是不是都照办。
   claude 那边额外验一次 `--safe-mode` 之下用户全局规则的痕迹仍然不在。

   **那条指令必须是纯文本动作（加一行字），绝不能是任何会碰工具的动作。**
   理由是 agy 有一个已知的同形陷阱：它在写盘被拒时返回 `status=SUCCESS`
   **加空正文**，与「这一轮没话说」在字节上完全一样。若把验收指令写成
   「建一个文件」，agy 回一个空正文时你分不出是**规则没读到**还是**写盘被拒**，
   这一条验收就失去判别力。`denied_actions` 的解析是另一片的事，
   本条验收设计成绕开它即可。

   同理，`renderIdentity` 这一路在 claude 上是否仍然生效**不需要重测**：
   载体还是那个 `--append-system-prompt-file`、那一个文件，
   `--safe-mode --restricted` 之下身份块照常注入是 `6530839` 当时实测过的，
   规则文本只是让那个文件的正文变长，没有引入新变量。
